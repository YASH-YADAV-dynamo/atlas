The problem

Every agent in the fleet starts from zero.

Browser agents are stateless about the web. Whatever one instance learned about a site is gone before the next instance opens its first tab.

  • The same exploration, again

    Ten agents refunding ten orders each rediscover where Orders lives and what Refund looks like. The site did not change; the work was repeated.

  • A model call per click

    Chaining round trips to decide each step costs model calls and seconds, and every call carries a page worth of context tokens.

  • Context preloaded, not pulled

    The usual fix is stuffing every tool and every page description into the prompt up front. Most of it is irrelevant to the task at hand.

How it works

A task is a route. Atlas finds it and only leaves it where the map ends.

  1. 01

    Locate

    Fingerprint the current page and find the node of the map the browser stands on.

  2. 02

    Plan

    One HydraDB shortest-path query returns the cheapest, most reliable route to the goal.

  3. 03

    Drive the known route

    Replay each known action in Chromium. No model in the loop.

  4. 04

    Explore only where the map ends

    At the frontier the model takes one step, and only one.

  5. 05

    Learn

    Every step is reported back, so the next agent drives what this one explored.

agent 1 "Refund order ORD-1005" empty map
MODELopen Orders
MODELopen order ORD-1005
MODELclick Refund, confirm
explored and saved to the graph
agent 2 "Refund order ORD-1017" same task type
MAPopen Orders
MAPopen order ORD-1017
MAPclick Refund, confirm
No model calls. one graph query planned it

Self-repair

When a site changes, the step that stopped working is penalised, the plan routes around it, and the model re-explores only that edge. Change events are kept in the graph.

An agent context layer

Context your agent pulls, not preloads.

Atlas keeps a live context store in HydraDB. Instead of loading every tool and every page into the prompt, your agent traverses the graph and pulls only what the current task needs: one query, not a chain of round trips.

  • Skills in a graph

    Routes that worked repeatedly are compressed into reusable skills your agent finds by goal.

  • Tool and MCP definitions in a graph

    Pages and the actions between them are nodes and edges with success rates, so tools are matched to the page, not dumped in a list.

  • Resolved entities

    Order ids, users and items already found are stored with where they were last seen. Recall, do not re-search.

  • Change events

    What stopped working, when, and which edge replaced it.

  • Graph traversal

    Shortest path by reliability and speed. Responses are compact and capped, which keeps context tokens low.

PRELOAD

Every tool definition and page description in the prompt before the task starts. More context tokens, more noise, and a model call to chain each step.

PULL

find_skills, then plan: the route for this goal from this page, nothing else. The model is asked only where the map ends.

Then tell it how to use Atlas

Paste this once Atlas is connected, or keep it in your agent's system prompt or project rules (CLAUDE.md, .cursorrules, AGENTS.md). It is the short version of "Use Atlas effectively".

Prompt: using Atlas
When you work on a website, use the Atlas MCP tools:
1. Write the goal once with {slots} and pass the values as params, e.g.
   goal_text "Open the first book in {category}", params {"category": "Travel"}.
   Keep the goal text identical every time you repeat the task.
2. Call atlas_find_skills with the site and goal, then atlas_plan with the
   site, goal, params and a short page summary (url, title, interactive elements).
3. Run the returned steps in your own browser without stopping to think.
   If a step does not reach its expected state, stop following the plan.
4. If needs_model is true, run any steps it returned, then choose the next
   action yourself.
5. After every step call atlas_report with from_state, the action, the new
   page summary, ok and ms. In an action set param OR value, never both.
   On the step that finishes the task, add goal_text, params and
   goal_reached=true.
6. Never send passwords, card numbers or other secrets to Atlas.

Connect your agent

Sixty seconds over MCP.

Add Atlas as an MCP server, or use the Route API, the Python SDK or trace import. The demo key is read-only on a pre-built map; a private key gives your agent its own map to write to.

Command line
No header support? Use this URL

Treat any URL that contains your key like a password. Streamable HTTP only; SSE is not offered. Endpoint: https://atlas.yashdynamo.fun/mcp

All clients

Plain HTTP from any language: locate the page, plan the route, report each step.

curl
curl -s -X POST https://atlas.yashdynamo.fun/v1/plan \
  -H "Authorization: Bearer $ATLAS_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"site": "shop", "state_id": 1,
       "goal_text": "Refund order 1042",
       "params": {"order_id": "1042"}}'

A thin typed client. Your agent step is called only where the map ends.

Python
from atlas_sdk import Atlas

atlas = Atlas("https://atlas.yashdynamo.fun", api_key, site="shop.example")
summary = atlas.session(driver).run(
    "Refund order 1042", {"order_id": "1042"}, fallback=my_agent_step)

FAQ

Questions builders ask.

Does Atlas run my browser?

No. The hosted server runs in planner mode: your agent drives its own Chromium, Playwright or cloud browser, and Atlas plans and learns. It never opens a browser or acts on a site itself.

What is stored?

Abstract pages (URL template, title and a signature of the controls, not the page text), actions with {slot} placeholders instead of values, goals, skills, resolved entities and change events. Nothing else.

Is my map private?

A private key gets its own namespace in HydraDB: nothing you report is visible to other keys. The public demo key is read-only on a shared map. Keys are stored only as keyed hashes.

What happens when a site changes?

The step that fails is penalised, the plan routes around it, and the model re-explores only that edge. The change is recorded as an event on the graph.

Which agents work with it?

Any MCP client over streamable HTTP, or any code that can call the Route API. The Python SDK wraps the loop for Playwright-style drivers.
