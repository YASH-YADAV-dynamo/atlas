Atlas documentation

Atlas is an agent context layer for browser agents: a live context store in HydraDB holding the pages of a site, the actions between them, skills, resolved entities and change events. Your agent pulls what the task needs instead of preloading it.

Quickstart

Hosted endpoint: https://atlas.yashdynamo.fun/mcp (MCP over streamable HTTP, bearer key on every request). Add it to your client, then run this loop inside your agent:

  1. atlas_find_skills with the site and the goal, to see what the map already knows how to do.
  2. atlas_plan with a summary of the current page. Execute the returned steps in your own browser.
  3. Where the plan says needs_model, let your model choose the next action, execute it, and call atlas_report.
  4. Next time, atlas_plan returns the whole route.
Example: Claude Code
claude mcp add --transport http atlas https://atlas.yashdynamo.fun/mcp \
  --header "Authorization: Bearer <key>"

Use for one-click setup and a key. Atlas never opens a browser in hosted mode: your agent drives its own Chromium or Playwright session.

Concepts

State
An abstract page: site, URL template, title and a signature of its interactive controls (not the page text). Every concrete page with the same signature is one state, so /orders/1042 and /orders/7 are the same node.
Action
One state-changing step between states: click, fill, select, check, press or goto, located by role and accessible name. Values are stored as {slot} placeholders, so a route learned for one order serves any other. Edges carry success counts and timings; the planner minimises cost by reliability and speed.
Skill
A route that proved itself repeatedly, compressed into one reusable hop. Found by goal with atlas_find_skills.
Entity
A resolved thing such as order_id 1042, stored with the action where it was last seen. atlas_recall answers "where did I see this?" without searching again.
Change event
When a learned action stops working, the failure is penalised, the plan routes around it and the event is recorded. Read recent changes through the atlas://site/{site}/changes resource or GET /v1/changes?site=.

A task is planned as one weighted shortest-path query over the graph in HydraDB. The model is asked only where the map ends (the frontier).

MCP tools

The hosted server runs in planner mode. Responses are compact JSON in a fixed token budget; long lists are cut and flagged truncated.

ToolCall it whenReturns
atlas_find_skillsStarting a task: what does the map already know how to do on this site? Input: site, goal_text.Up to 5 skills with id, name, parameters and reliability.
atlas_planYou know the current page and want the route to a goal. Input: site, snapshot_summary, goal_text, params.The page's state_id and steps with the expected next state, or needs_model with a reason.
atlas_recallYou need where an entity was last seen. Input: entity_type, key.Found, the page's state id and URL template.
atlas_reportAfter every step you executed, to teach the map. Input: site, from_state, action, to_snapshot_summary, ok, optional event_id, goal_text, params, goal_reached.The new state_id, whether it was known. Safe to retry with the same event_id.

Resources: atlas://sites (mapped sites and sizes) and atlas://site/{site}/changes. With the public demo key the tools are read-only: atlas_report returns a read-only error. Self-hosted stdio mode can also expose atlas_run and atlas_act, where Atlas drives a local browser itself.

Route API

The same map over plain HTTP, authenticated with the same bearer key. Three calls:

locate, plan, report
# 1. Where am I? Send a snapshot of the current page.
POST /v1/locate  {"site": "shop", "snapshot": {"url": "...", "title": "...", "elements": [{"role": "link", "name": "Orders"}], "text": "..."}}
# -> {"state_id": 12, "known": true}

# 2. How do I get to the goal?
POST /v1/plan    {"site": "shop", "state_id": 12, "goal_text": "Refund order 1042", "params": {"order_id": "1042"}}
# -> {"route": [{"action": {...}, "expect_state": 14, "reliability": 0.97}], "needs_model": false, "reason": "route_found", ...}

# 3. Teach the map what happened after each step you executed.
POST /v1/report  {"site": "shop", "from_state": 12, "action": {...}, "to_snapshot": {...}, "ok": true, "ms": 180,
                  "event_id": "run1-0", "goal_text": "Refund order 1042", "params": {"order_id": "1042"}, "goal_reached": false}
# -> {"state_id": 14, "known": true, "duplicate": false}

Also: GET /v1/map/{site}, GET /v1/changes?site=, GET /v1/skills?site=, GET /healthz. Plan reasons: route_found, unknown_goal, no_route_within_max_steps, missing_params. Reports are idempotent on event_id.

Python SDK

A thin client over the Route API. It depends on httpx only.

Python
from atlas_sdk import Atlas

atlas = Atlas("https://atlas.yashdynamo.fun", api_key, site="shop.example")
summary = atlas.session(driver).run("Refund order 1042", {"order_id": "1042"}, fallback=my_agent_step)
print(summary)  # RunSummary(success=True, steps=5, map_steps=5, fallback_calls=0)
  • driver has snapshot() (url, title, elements as role/name dicts) and act(action).
  • fallback(snapshot, goal, params) is your own agent step. It is called only where the map ends and returns one action, or None when the goal is done.
  • Parameter values are replaced by {slot} placeholders before a step is reported. API errors raise AtlasApiError(status, code, message).

Trace import

Seed a map from runs you already recorded, without re-exploring. A trace is JSON Lines: one step per line with run_id, index, site, before and after snapshots, the action, and optionally ok, ms, goal_text, params and goal_reached. Unknown fields are rejected, and the whole file is validated before anything is imported.

Shell
ATLAS_API_URL=https://atlas.yashdynamo.fun ATLAS_API_KEY=your-key \
python -m atlas.import_trace runs.jsonl
# {"steps":5,"runs":1,"new_states":6,"duplicates":0,"failed_steps":0,"goals_linked":1}

Re-importing the same file counts every step as a duplicate. TraceRecorder wraps any driver to record runs as you go. Never record real credentials: use templated actions (a password field filled with {password}).

Connect

Atlas speaks MCP over one transport, streamable HTTP, and your client reaches it in one of two ways. Replace <key> with the demo key from GET /v1/mcp-info or a private key from POST /v1/keys. to fill these in with your key.

Remote (HTTP)

The client connects directly to the hosted URL and sends the key in an Authorization header. Use it whenever your client supports remote MCP servers with headers. Nothing to install.

{
  "mcpServers": {
    "atlas": {
      "type": "http",
      "url": "https://atlas.yashdynamo.fun/mcp",
      "headers": { "Authorization": "Bearer <key>" }
    }
  }
}

Some clients name the transport field differently or leave it out; the URL and the header are what matter.

No header support? Some clients take only a URL. Put the key in the path:

https://atlas.yashdynamo.fun/mcp/k/<key>

It is the same endpoint with the same key, map, limits and read-only rule for the demo key. Treat that URL like a password: anyone who has it can use your key. Atlas masks the key in its own access log, and a wrong key gets 401 without being echoed.

Local (stdio)

The client launches a command and talks to it over stdin and stdout. For hosted Atlas the command is the standard mcp-remote bridge, which forwards stdio to the hosted URL (it needs Node.js):

{
  "mcpServers": {
    "atlas": {
      "command": "npx",
      "args": ["-y", "mcp-remote", "https://atlas.yashdynamo.fun/mcp",
               "--header", "Authorization: Bearer <key>"]
    }
  }
}

The same command by hand, or through the key-in-path URL if passing a header is awkward:

npx -y mcp-remote https://atlas.yashdynamo.fun/mcp --header "Authorization: Bearer <key>"
npx -y mcp-remote https://atlas.yashdynamo.fun/mcp/k/<key>

A self-hosted Atlas can instead run its own stdio server, python -m atlas.mcp, which can also drive a local browser (see Self-hosting in the MCP guide).

Open in your editor

Cursor and VS Code register install links, so the connect dialog offers one-click buttons that add the server for you after a review prompt.

The response carries an mcp-session-id header. Send it on the following requests. A session belongs to the key that created it. The legacy SSE transport is not offered.

Keys and isolation

KeyFromMapWrites
Demo keyGET /v1/mcp-infoshared, pre-mappedno
Private keyPOST /v1/keysyour own, empty at firstyes

A private key gets its own namespace: nothing you report is visible to other keys. The key is shown once; Atlas stores only a keyed hash, so a lost key cannot be recovered. The same key works for the REST and MCP views of your map. Limits apply to key creation, request rate and stored steps per key (over the rate limit you get 429).
